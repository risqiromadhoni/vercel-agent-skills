# skill-bench

Bench for the React skills. It checks that the Correct examples in `skills/react-best-practices` and `skills/composition-patterns` still compile and build in two real frameworks:

- `fixtures/nextjs`: Next.js 16 App Router, Cache Components on, React Compiler opt-in.
- `fixtures/tanstack-start`: TanStack Start (SSR), Vite.

Tier 1 (this package today) is deterministic: each rule's Correct example is ported into a fixture, then `tsc` and the production build must pass. Tier 2 (agent eval with and without the skill, scored by a compiler-API check) is planned for Phase F; `eval`, `report` and `selftest` are placeholders until then.

## Layout

```
packages/skill-bench/
  package.json  pnpm-lock.yaml  .gitignore  README.md
  mapping/                       rule -> framework status and note (one file per skill)
    react-best-practices.json
    composition-patterns.json
  scripts/
    sync-examples.mjs            seed fixture stubs from Correct examples
    check-example-hashes.mjs     compare Correct-code hashes with the manifests
    lib/rules.mjs                shared helpers (list, parse, hash, manifest I/O)
  fixtures/
    nextjs/                      create-next-app@16 output, pinned
      src/rules/                 one stub per rule, plus index.ts (generated from the manifest)
      app/rules/page.tsx         imports src/rules so `next build` covers it
      rules.manifest.json
    tanstack-start/              hand-written per the TanStack Start "build from scratch" guide
      src/rules/                 one stub per rule, plus index.ts
      src/routes/rules/          route that imports src/rules
      src/routeTree.gen.ts       generated by the Vite plugin and committed
      rules.manifest.json
  results/                       eval output (gitignored except .gitkeep)
```

## Commands

Run from `packages/skill-bench`. CI uses pnpm 10.24.0 on Node 20; if your local pnpm differs, use `npx -y pnpm@10.24.0 <script>`.

| Command | What it does |
|---|---|
| `pnpm fixtures:install` | Installs both fixtures with `--frozen-lockfile`. |
| `pnpm typecheck` | `tsc --noEmit` in both fixtures. |
| `pnpm build` | Production build of both fixtures. For the React Compiler variant of Next: `REACT_COMPILER=1 pnpm --dir fixtures/nextjs run build`. |
| `pnpm sync --skill=<skill> --fw=<fw> [--rule=<id>] [--dry-run]` | Writes a stub for each rule that lacks one and records `{ "status": "auto", "sourceHash" }` in the fixture manifest. Never overwrites a stub or an `adapted` entry. Then regenerates `src/rules/index.ts` from the manifest (one `import * as` per entry whose stub exists). The index is regenerated even with `--dry-run`, since it changes no stub or manifest. Summary JSON on stdout. |
| `pnpm check-hashes [--fw=<fw>] [--skill=<skill>] [--accept <rule-id>] [--adapted <rule-id>]` | Recomputes each rule's Correct-code sha256 and compares it with the manifest. Exits 1 on drift, a stale or missing entry, a missing stub, or an unmapped rule. With no flags it checks both fixtures and both skills. `--accept` re-stamps one entry's hash. `--adapted` sets one entry's `status` to `"adapted"` and keeps its hash; the stub must exist. Whenever the manifest is written, `src/rules/index.ts` is regenerated. |
| `pnpm selftest` | Placeholder. Exits 0. |
| `pnpm eval`, `pnpm report` | Placeholders. Exit 0. |

`<fw>` is `nextjs` or `tanstack-start`. `<skill>` is `react-best-practices` or `composition-patterns`.

## Adding or updating a rule

1. **Sync.** `pnpm sync --skill=react-best-practices --fw=nextjs --rule=<rule-id>`. This writes `fixtures/nextjs/src/rules/<rule-id>.tsx` with two header lines, `// SOURCE:` and `// HASH:`, followed by the Correct code unchanged. The manifest entry is `status: "auto"`. It also regenerates `src/rules/index.ts`, so the rule is compiled by the fixture build and not only by `tsc`.
2. **Adapt.** Edit the stub until it compiles, and make the same change for each framework the mapping marks `port` or `equivalent`. Then run `pnpm check-hashes --adapted <rule-id>` (add `--fw=<fw>` to flip one framework only). It sets that manifest entry's `status` to `"adapted"` and keeps the hash, so you don't edit the JSON by hand. Sync skips `adapted` entries, so it won't overwrite your work.
3. **Accept the hash.** After a source change, once you have re-checked the port against the new Correct example, run `pnpm check-hashes --accept <rule-id>`. This updates `sourceHash` and the `// HASH:` line. Do not accept without re-checking; accepting only re-stamps the hash.
4. **Seed and check.** Tier 2 seed and `check.mjs` files (planned, Phase F) go under `fixtures/<fw>/seeds/<rule-id>/`.
5. **Verify.** `pnpm check-hashes && pnpm typecheck && pnpm build`.

If a rule's source changes and its stub is still `auto`, `check-hashes` fails with hash drift. Delete the stub and re-run sync to regenerate it. Stubs are generated from the source only when the file is absent.

## Mapping and the N/A policy

Each entry in `mapping/<skill>.json` gives a status per framework plus a note:

- `port`: the Correct example is ported with the same mechanism. It must typecheck and build.
- `equivalent`: a different mechanism gives the same behaviour (for example `React.lazy` in place of `next/dynamic`). It must typecheck and build. The note names the mechanism.
- `na`: the framework has no equivalent of the rule's feature. Sync and check skip it, and the report lists it as N/A. N/A is neither a pass nor a failure. The note must say why. Current N/A entries are TanStack Start for `server-use-cache-directive`, `server-async-request-apis`, `server-connection-over-force-dynamic` and `server-after-nonblocking`.

Every rule file in `skills/<skill>/rules/` must have a mapping entry for each framework; `check-hashes` reports unmapped rules as failures. Rule IDs are file basenames without `.md`. Files starting with `_` are skipped. A rule is seeded from the first example whose label contains the whole word "Correct". `Incorrect` is not a match. Rules with no Correct example are skipped by sync and not checked.

## Fixture notes

- Next: `create-next-app@16` with non-interactive flags, then edited. Google Fonts were removed so builds need no network. `cacheComponents` and `partialPrefetching` are on. `reactCompiler` follows `REACT_COMPILER=1`. Versions are exact pins in `package.json`.
- TanStack Start: `@tanstack/react-start` is pinned to 1.168.61, the newest release whose vite peer accepts vite 7. Releases from 1.169.0 onward require vite 8. Move both together when the fixture moves to vite 8.
- `verbatimModuleSyntax` is off in the TanStack tsconfig, as the TanStack docs recommend.
- Both fixtures pin pnpm 10.24.0 in `packageManager` and commit `pnpm-lock.yaml`.
